# CodeLearn: аудит і план нового проєкту

Дата: 14 листопада 2026 року. Статус: пропозиція до реалізації.

## 1. Мета та межі аудиту

Створити окремий чистий проєкт, зберігши ідею CodeLearn, навчальні сценарії та характер продукту. Основні вимоги: розширення функціональності без перероблення основи, багатомовність від першого екрана, кращий дизайн, звуковий відгук, надійний прогрес і робота без мережі.

Переглянуто дерево репозиторію, залежності, платформні конфігурації, моделі, маршрути, ключові екрани й провайдери, авторизацію, збереження прогресу, нагороди, локалізацію, перевірку коду, інструменти експорту/перекладу та тести. Пораховано JSON-контент усіх мов. Локально запущено вебверсію; візуально переглянуто онбординг, головний екран, каталог, сторінку курсу й відкриття уроку без входу в акаунт.

Це аналіз наявної реалізації, а не підтвердження працездатності всіх інтеграцій. Не перевірялися реальні облікові записи, доставлення листів, серверні правила доступу розгорнутого Firebase, синхронізація двох фізичних пристроїв і нативні релізні збірки. Наявність файлів перекладів не означає редакторську перевірку їхньої якості.

## 2. Ідея продукту, яку зберігаємо

Основний цикл: обрати навчальний напрям → пройти коротку теорію → відповісти на питання → виконати практичне завдання → отримати прогрес і винагороду → побачити наступний крок.

Навчання підсилюється щоденною звичкою, рівнями, досягненнями й відчуттям власного розвитку. Найцікавіші відмінності: інтерактивний Git, CLI з файловою системою, карта навичок і портфоліо рішень. Це має залишитися впізнаваною основою нового застосунку.

Розширені quiz-віджети існують, але перевірений англійський JSON-контент містить лише multiple choice, а основний екран не перемикає renderer за `question.type`. Hint tokens накопичуються в магазині; у переглянутому коді уроку їхнього списання не знайдено. Ці функції потрібно явно відмітити як частково інтегровані.

`tool/auth_api_example` — окремий приклад Express API з пам'яттю процесу як сховищем; Flutter використовує Firebase-сервіси. Не вважати цей приклад готовим backend застосунку.

## 4. Основа нового проєкту

Пропозиція: зберегти Flutter і підхід Riverpod/go_router, створити модульний застосунок із чіткими залежностями. Зміна фреймворку сама собою не усуває перелічені проблеми. Версії залежностей перевірити й зафіксувати при створенні проєкту.

```text
new-project/
  app/
    lib/
      app/                 bootstrap, session lifecycle, router, composition
      foundation/          errors, clock, logging, platform adapters
      design_system/       themes, typography, shared visual components
      l10n/                ARB та згенерований доступ до UI-перекладів
      features/
        auth/
        catalog/
        learning/
        practice/
        progress/
        rewards/
        journey/
        portfolio/
        profile/
        settings/
        support/
      infrastructure/      local DB, sync, remote transport, audio, notifications
    test/
    integration_test/
  content/                 catalog, schema, lessons, translations, manifests
  tools/                   import, validation, translation preparation
  backend/                 trusted mutations and API contracts
  docs/                    product inventory, decisions, release instructions
```

У функціональних модулях використовувати `presentation`, `application`, `domain`, `data` лише там, де для них є реальна відповідальність. Не створювати порожніх шарів, класу на кожну дію чи універсального repository для всіх сутностей. Окремі пакети виділяти, коли з'явиться реальна потреба незалежного використання або контролю залежностей.

Напрям залежностей: екран → controller/application → domain і repository contract. Реалізація repository працює з локальною БД та віддаленим джерелом. Domain не імпортує Flutter, Firebase чи UI-локалізацію. Моделі Firestore/JSON перетворюються на межі, а не передаються екраном як `dynamic`.

Модулі спілкуються через явні контракти. Завершення уроку — один application-сценарій з результатом: стан завершення, XP breakdown, зміна streak, винагороди, відкриті досягнення та статус синхронізації. Звук, анімації й notifications реагують на успішний результат; їхня помилка не скасовує навчальний прогрес. Глобальний event bus не потрібен для кожної взаємодії.

Масштабування перевіряється конкретно: новий курс додається як контент; нова мова — як перевірений пакет перекладів; новий renderer вправи — через контракт; зміна backend не вимагає переписування екранів. Великі списки завантажуються частинами, історія не читається повністю для кожної картки.

## 5. Дані, backend і робота без мережі

Початкове рішення — зберегти Firebase Auth і розглянути Firestore з довіреними серверними командами для навчального прогресу та економіки. Остаточний вибір залежить від наявних користувачів, запитів до даних і потрібних платформ; зараз немає доказу, що потрібна повна заміна backend або мікросервіси.

Локальна БД з транзакціями зберігає завантажений контент, сесії уроків, відповіді, чернетки, портфоліо та чергу синхронізації. SharedPreferences залишається для простих налаштувань. Контракт repository приховує різницю між гостьовим і авторизованим режимом. Такий поділ відповідає [рекомендаціям Flutter для offline-first](https://docs.flutter.dev/app-architecture/design-patterns/offline-first).

Основні сутності: Course, Module, Lesson, Exercise, LearningSession, Attempt, Completion, ActivityDay, RewardTransaction, InventoryItem, PortfolioEntry, UserPreferences. Для контенту й даних користувача потрібні версії схем і контрольовані міграції.

Правила цілісності:

- Стабільний ключ завершення на користувача й урок; повтор запиту не додає винагороду знову. Окремо визначити поведінку для нової редакції уроку.
- Спроба та завершення — різні сутності: повторення дозволене, дублювання винагороди контролюється політикою.
- Сервер перевіряє дозволені нагороди й покупки; клієнт не задає довільний XP. Для симуляторів без серверної перевірки явно визначити межі довіри.
- Зміни стану й запис операції виконуються атомарно в межах серверної команди; повідомлення обробляються повторно без повторного ефекту.
- Стани черги: pending, syncing, synced, failed; повтори після збоїв і відновлення після закриття застосунку.
- Офлайн-завершення зберігається одразу; серверні винагороди можуть показуватися як очікувані до підтвердження. Витрати wallet потребують визначеної політики; початково покупки доступні онлайн.
- Completion об'єднуються без втрат; wallet має серверний журнал; налаштування мають явне правило конфліктів; для портфоліо не можна мовчки перезаписувати дві різні редакції.
- День streak визначається календарною датою у погодженому часовому поясі, а не різницею у 24 години. Відокремити запуск застосунку, daily check-in та навчальну активність.
- Вихід і зміна акаунта ізолюють локальні дані й незавершені операції. Перехід гостя в акаунт має явний сценарій злиття.

## 6. Багатомовність від першого дня

Мають існувати окремі налаштування `uiLocale`, `learningLocale` та `programmingLanguage`. Вибір Python не визначає мову тексту; перемикання UI не скидає сесію уроку.

**Інтерфейс:** ARB + Flutter gen-l10n; типізовані повідомлення, параметри та ICU plural/select. Повні фрази з placeholders, без склеювання перекладених шматків. Форматування дат, чисел, відносного часу й кількостей за локаллю. Помилки надходять як стабільні коди; локалізуються біля UI. Підхід спирається на [офіційну документацію Flutter](https://docs.flutter.dev/ui/internationalization).

**Навчальний контент:** мовонезалежна структура з постійними ID для lesson/slide/exercise/question/option; мовні пакети містять текст. Код, правильна відповідь за ID, test input/output і правила виконання не перекладаються автоматично. Текстові варіанти відповіді та фрагменти коду мають різні типи. Перестановка або переклад варіантів не повинні змінювати правильну відповідь.

**Публікація:** пакет мови має версію, стан перевірки й сумісність із версією контенту. Переклад готується заздалегідь, перевіряється схемою та редактором і публікується пакетом. Машинний переклад може допомагати підготовці; користувацький урок не чекає зовнішнього перекладача. Неповний урок використовує цілий перевірений fallback із повідомленням, замість випадкового змішування мов.

**Відображення:** підтримка RTL від початку; відступи через start/end, іконки напрямку за змістом, текст коду лишається LTR. Шрифти з підтримкою потрібних абеток і локальні font assets для передбачуваної роботи без мережі. Перевірки довгих німецьких рядків, українських множин, арабської, CJK та збільшеного шрифту.

**Автоматична перевірка:** відсутні й зайві ключі, типи placeholders, множини, невідомі ID, пошкодження code/test fixtures, застарілий переклад, переповнення компонентів. Мова стає доступною як повністю підтримана лише після проходження критеріїв. Спочатку повністю перевірені українська й англійська; решта наявних 16 мов проходять імпорт і перевірку, а не втрачаються.

## 7. Навчальний рушій і перевірка коду

Окремий `LearningSession` керує етапами, порогом quiz, відкриттям практики, чернетками, повторними спробами й завершенням. UI лише показує поточний стан і передає дію користувача.

Для вправ потрібен типізований контракт: вхід, виконання/перевірка, diagnostics, результати кожного тесту, підсумковий статус. Невідома мова дає явну помилку підтримки, а не запускається як Python. Правило порівняння output належить вправі; регістр не ігнорується глобально.

Git і CLI залишаються керованими навчальними симуляторами. SQL доцільно виконувати над ізольованою навчальною БД та порівнювати результати. Для Python/JS/C++ треба зробити технічну пробу: локальні обмежені вправи проти справжнього ізольованого виконання. Для React — окремо визначити перевірку компонента, а не видавати JS-перевірку за браузерний React runtime.

Повне віддалене виконання довільного коду — окремий етап із лімітами часу, пам'яті, output і мережі та ізоляцією. Для офлайну позначається доступність конкретної вправи. Не обіцяти одночасно повні мови, усі платформи й повний офлайн до перевірки цих обмежень.

## 8. Оновлення дизайну

Зберегти синій/фіолетовий акцент, темну й світлу теми, кольори напрямів і святкування прогресу. На переглянутих широких екранах великі вертикальні картки та заголовки займають значну частину висоти; уроки й курс мають помітно різні поверхні. Оновлення має об'єднати їх у послідовну систему.

- Єдині шкали типографіки, відступів, радіусів, поверхонь, статусів, іконок і руху.
- Головна: продовження уроку як основний блок; ціль дня та streak поруч; статистика й бонуси нижче.
- Каталог: компактні картки, пошук, фільтри, зрозумілі рівні й рекомендований напрям.
- Курс: модулі, залежності, зрозуміла причина блокування й наступний доступний урок.
- Урок: читабельна теорія, очевидний прогрес етапів, один основний CTA; редактор, умова й результати зручно співіснують. Клавіатура не перекриває Run та output.
- Git/CLI: граф або файли поруч із командною зоною на широких екранах; доступне перемикання на телефоні.
- Journey: карта як огляд розвитку, детальна статистика окремо. «Слабкі місця» будуються з відповідей і помилок, а не лише відсотка проходження.
- Навігація: мобільна нижня панель; на широких екранах бічна навігація й обмежена ширина тексту. Без втрати стану вкладок і з прямими посиланнями за ID.
- Кожний екран має loading, empty, error, offline та retry стани. Доступність: контраст, фокус, семантика, screen reader, великий шрифт і reduced motion.

До реалізації всіх екранів підготувати інтерактивний прототип головної, каталогу, уроку й завершення. У ньому перевірити українську, довгі рядки та RTL. Цей аудит не містить готового редизайну; він визначає напрям і критерії.

## 9. Звуки й тактильний відгук

У `assets` зараз немає аудіофайлів, окремого sound-сервісу й аудіозалежності в pubspec також немає. Звуки системних notifications — інший механізм.

| Подія | Пропонований відгук |
| --- | --- |
| Правильна відповідь | Короткий м'який позитивний сигнал |
| Неправильна відповідь | Тихий нейтральний сигнал і чітке текстове пояснення |
| Успішна практика | Коротке підтвердження |
| Завершення уроку | Невелика мелодія успіху |
| Новий рівень / досягнення | Більш виразне святкування з пріоритетом над дрібними звуками |
| Серія днів / отримання бонусу | Короткий відгук відповідної події |

Один audio adapter і координатор відгуку керують попереднім завантаженням, гучністю, пріоритетами й обмеженням частоти. Не грати все одночасно й не повторювати винагороду через rebuild або повторну синхронізацію. Звук не може бути єдиним носієм інформації.

Окремі налаштування: sound effects, гучність, haptics. Повага до беззвучного режиму, audio focus, дзвінків і фонового стану; на вебі врахувати потребу жесту користувача для запуску аудіо. Аудіо локальне, коротке, з підтвердженими правами використання. Фонова музика початково не потрібна.

Кандидат для технічної проби — [audioplayers](https://pub.dev/packages/audioplayers), з перевіркою керування audio session на цільових платформах; за потреби [audio_session](https://pub.dev/packages/audio_session). Остаточний вибір після перевірки затримки й поведінки на реальних пристроях.

## 10. Послідовність переписування та критерії готовності

| Етап | Робота | Що підтверджує готовність |
| --- | --- | --- |
| 1. Специфікація | Матриця функцій, станів і переходів; точні правила XP/streak/quiz; платформи; карта даних | Кожна стара механіка має рішення: перенесена, виправлена або явно відкладена |
| 2. Основа | Новий проєкт, середовища dev/staging/prod, модулі, DI, router за ID, logging, CI | Запуск із прямого URL, зрозумілі помилки bootstrap, статична перевірка й базові тести |
| 3. Дизайн і локалізація | Design system, прототип ключових екранів, ARB, мови UI/навчання, RTL | Ключовий сценарій читабельний українською/англійською та перевірений з RTL і довгим текстом |
| 4. Контент | Схема, валідатор, імпорт 18 курсів і 145 уроків, звірка з Dart-джерелом, переклади | ID й правильні відповіді збережені, code/test fixtures не пошкоджені; звіт про неповні переклади |
| 5. Наскрізний сценарій | Один курс: каталог → теорія → quiz → практика → завершення → прогрес; чернетка й один sound effect | Працює після закриття/відкриття й без мережі; повторне завершення не множить XP |
| 6. Backend і синхронізація | Сесія, гість → акаунт, outbox, серверні команди, конфлікти, permissions | Два пристрої, повтор запиту, offline/reconnect, вихід і зміна акаунта проходять перевірку |
| 7. Усі типи практики | Git, CLI, SQL, інші мовні адаптери; визначення реального runtime | Усі заявлені типи мають коректні тести, зупинку/ліміти й зрозумілу доступність офлайн |
| 8. Повний продукт | Achievements, rewards/shop, Journey, portfolio, profile, support, reminders | Кожна функція з матриці має робочий сценарій; hints і косметика реально використовуються |
| 9. Полірування | Повний sound pack, motion/haptics, доступність, performance, мовна редактура | Немає дублікатів звуку, перевантаження анімаціями, втрати чернеток і переповнення перекладів |
| 10. Перехід і реліз | Міграція даних, staging-прогін, релізне підписування, поетапне розгортання й rollback | Узгоджені прогрес/XP/портфоліо до й після переносу, повторний запуск міграції без дублювання |

Старий застосунок лишається джерелом поведінки до завершення міграції. Не копіювати весь `lib`, build-каталоги, старі конфігурації й backup-файли в новий проєкт. Переносити тільки перевірені ресурси, матеріали й тести поведінки. Новий і старий застосунки можуть працювати поруч; для цього потрібні окремі app IDs та ізольовані середовища.

Частина нових механік потребує продуктових рішень: чи повторне проходження приносить бонус, що саме продовжує streak, як витрачаються hints, чи обов'язкові 10 питань на кожний урок, чи quiz-поріг 60% залишається. Наявне автоматичне доповнення до 10 питань містить шаблонні завдання; кількість не повинна підміняти якість навчання.

## 11. Перевірки

Під час аудиту: `flutter test --no-pub` — усі 30 тестів пройшли. `flutter analyze --no-pub` — 49 зауважень, з них 3 warnings і 46 info; помилок рівня error немає. Це не свідчить про перевірку всіх функцій: поточні тести переважно локальні й не покривають основні міжмодульні ризики.

Для нової версії пріоритетні перевірки:

- Domain: XP breakdown, повтор completion, streak на межі дня/DST, місії дня, витрати й inventory.
- Дані: транзакції, повтор повідомлення, crash між записами, два пристрої, account isolation, міграція версій.
- Практика: різні input для кожного test case, проходження всіх обов'язкових тестів, регістр output, timeout/cancel, невідомі мови, еквівалентні SQL-рішення.
- Контент: унікальні й існуючі ID, залежності без циклів, валідні відповіді, сумісні переклади, перевірені рішення.
- UI: відновлення уроку й чернетки, клавіатура, прямі посилання, великий текст, RTL, light/dark, offline/error/retry.
- Backend: правила доступу, відхилення довільного XP, неавторизованих витрат і повторних claims.
- Audio: один відгук на одну подію, пріоритети, mute, background, виклики й навушники на реальних пристроях.

## 12. Що потрібно визначити перед реалізацією

Початкове припущення для планування: Android та iOS як основні платформи, web для навчання на великому екрані. Desktop не оголошувати підтриманим лише через наявність папок.

Потрібно уточнити, чи вже є реальні користувачі й дані, які обов'язково переносити; які платформи мають бути в першому релізі; які мови мають пройти повну редакторську перевірку першими; чи потрібен повноцінний запуск коду всіх мов відразу. Ці відповіді впливають на обсяг і порядок робіт, але не заважають підготувати чисту архітектурну основу.

Production-код під час аудиту не змінювався. Коміти не створювалися. Наявна до аудиту зміна `ios/Podfile.lock` не редагувалася.
